---
name: schedule
description: Create, inspect, pause, cancel, or run persistent local schedules for commands or prompts to existing coding agent sessions in cmux, Orca or tmux. Use when the user requests a reminder, recurring check, or delayed session wake on this computer.
---

Use the bundled CLI at `../../dist/cli.mjs`, resolved relative to this skill directory. It requires Node 22 or newer. No model API credentials or package installation are needed.

1. Inspect `node <plugin-root>/dist/cli.mjs status` and `list`. Preserve existing schedules. Every session, coding agent and provider home on this computer shares one global store and one daemon; never create a project-specific store or set `AGENT_SCHEDULER_HOME` (it exists only for tests).
2. Turn the user's authorized task into a schedule JSON file using [the schema](../../docs/schedules.md). Set a finite `maxRuns` and `expiresAt`. Use one schedule per monitored worker, with the supervisor as the delivery destination. Confirm missing time/timezone or destination identity when it affects delivery. Scheduling never grants new permissions for the future prompt.
3. Address the receiving session through the terminal manager it runs in (`cmux`, `orca` or `tmux`), whichever coding agent CLI it is. Run `terminals` to list receivers with their agent, session and cwd, and pick the exact one. Never create another model session or change its account. Terminal input is intended for a dedicated receiver: do not append to a user's unfinished prompt or target a terminal without a running agent. Newlines are flattened and control characters are rejected.
   Write the prompt yourself from the actual context of this conversation and the receiver: the goal, what to inspect, the completion criteria, what to do when blocked, and the authorized limits. Write it for a person reviewing the schedule as much as for the receiver. Do not generate it in a wrapper script, add opaque markers, or wrap terminal delivery in a `command` target.
   For cmux, keep the `agent` binding that `terminals` reports so the schedule follows that agent process only (it survives `/clear` and `/resume`).
   Choose `mode`: `goal` when the receiver should keep working across turns until a verifiable condition holds (sent as `/goal <prompt>`; it replaces the session's current goal, so prefer a one-shot trigger); otherwise `prompt` for a single check or instruction.
4. Register with `node <plugin-root>/dist/cli.mjs put <file>`. Registration (and `resume`) starts the detached global daemon when it is absent; the daemon is not tied to your session. Read back `list` and `status`; report the schedule ID, destination, next time, expiry, the daemon status and the management page URL. A wake starts a real agent turn and can consume model quota; ordinary timer ticks do not.
5. Use `pause ID`, `resume ID`, or `remove ID` for changes, or the management page served by the daemon (`ui` prints its URL). The daemon pauses a schedule whose receiver no longer runs an agent, and the plugin's session-end hook removes the schedules addressed to an ending session's terminal. Pause/remove does not recall a delivered prompt. At completion or user-requested stop, remove the relevant schedule and preserve its receipts.

When a receipt is `uncertain` or an `intent` is left after a crash, inspect the receiving terminal and command effects first. Do not resend or switch transport automatically. Stop the daemon, confirm the owner has exited, then use `resolve ID RUN` to acknowledge without replay. `unlock store|daemon` only removes a lock whose recorded process is absent on this host. Unknown/live owners block recovery. Do not delete locks or edit runtime state manually.

The scheduler only executes declared commands or submits text. It does not decide whether a worker is blocked, claim a merge is complete, or mark tasks done. Use a cheap command target for mechanical checks; wake a supervisor only when model judgment is needed. Keep task-specific decisions in the existing project context.
